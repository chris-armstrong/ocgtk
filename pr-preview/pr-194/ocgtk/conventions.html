Who this page is for

This page explains how the bindings are organised. It is meant for both those familiar with GObject based libraries like GTK (maybe from C or other languages) as well as those who are new to GObject, GTK and OCaml.

Background on GObject

GObject (or the GLib Object system) defines an portable object-model for C-based code in a way that makes it straightforward to bind and use from other languages. GObject is the cornerstone of GTK and its dependencies, as well as libraries that depend on it like GNOME's adawaita.

At the core of GObject is a generic, introspectable type system called GType. This runtime description facilitates cross-language bindings, which can be either done dynamically at runtime (e.g. in loosly typed languages like JavaScript or Python) or used to generate metadata for procedurally generating binding code for strongly typed languages via GObject Introspection (like Rust or OCaml) - we've used the latter approach.

The GType system can handle primitives like strings, numbers, booleans, etc., as well as objects and classes (using a single-parent inheritance structure but allowing multiple interfaces, similar to Java or Objective-C). It contains enough metadata to specify how reference counting should operate (for objects) and transfer of ownership (for both objects and primitives) so that memory management can be managed from the host language runtime.

GObject also defines closures, which allow the C-language code to call back into the host language; and signals, which are events emitted on an object, that can be listened to via a closure. (You will interact with signals by registering an OCaml callback function - closures are an internal detail).

Overview: The two layers

OCaml is a functional language with an object-oriented layer. Because GTK is object-oriented but OCaml requires C-bindings to occur in its functional / module layer, we provide two sets of bindings:

* Layer 2: classes and objects: this is an object-oriented binding to GObject * Layer 1: functions: a pure functional binding to GObject

flowchart TD
  C["C library (libgtk-4, libgio-2.0, ...)"]
  L1["Layer 1: Gtk.Wrappers.Button
  type t, one function per C function"]
  L2["Layer 2: Gtk.Button
  class type button_t, class button, new_* constructors"]
  APP["Your code"]
  C --> L1 --> L2
  APP -- "usually" --> L2
  APP -. "interop, low level" .-> L1

(Internally, the C binding layer is known as "Layer 0").

You can use each layer independently of the other one, but because the classes layer wraps around the functional layer, you can also move back and forth as needed.

  • Layer 1 (the Wrappers modules): one module per class, an abstract handle type t, one function per C function. Closest to the C API.
  • Layer 2 (the class modules): one module per class, holding an OCaml class type, a class, and constructors. Methods, signals and properties are object methods. This is the layer most code should use.
  • Both layers wrap the same objects; you can move between them (see Converting between the layers).
  • When to use Layer 1: interop, functions with no Layer 2 form, or avoiding objects in performance-sensitive code (check that this claim holds before writing it).

Libraries and namespaces

ocgtk is a single opam package, but internally it contains one library per GObject namespace, such as `Ocgtk_gtk`.

In each library, you'll find a layout like the following:

Ocgtk_<namespace>
  +- <Namespace>           (* class and interface modules (layer 2) *)
     +- Wrappers           (* functional modules (layer 1) *)
  +- <Namespace>_enums     (* enumerations *)
  +- <Namespace>_constants (* constants *)

For example, GTK has a layout like the following:

Ocgtk_gtk
  +- Gtk           
     +- Wrappers           
  +- Gtk_enums     
  +- Gtk_constants 

  (* These are specific to GTK *)
  +- GMain          (* runloop and initialisation *)
  +- GVersion       (* GTK version information *)

These are designed so that you can open `Ocgtk_gtk` and then refer to each class module, enumeration and constant directly e.g.:


open Ocgtk_gtk.Gtk

let () =
  let _ = Ocgtk.GMain.init () in
  let window = Window.new_ () in
  window#set_gravity `LEFT;
  window#set_default_width 300;
  window#set_default_size 200;


  Ocgtk.GMain.main ()

Anatomy of a class module

Known internally as "Layer 2", this is the recommended way of interacting with ocgtk. Each GObject class and interface is mapped to an OCaml class which you can invoke methods on, but you don't instantiate them directly.

Each class and its type is declared in a separate module. The module is named after the GObject class. It will also contain one or more constructor functions that instantiate an object of that class for you.

(Each class has been put its own module for several reasons. The first is practicality: OCaml's compiler won't easily handle a file with hundreds of class types and classes, each with dozens of methods. By splitting them up, they can also be compiled in parallel (which is much faster), and unused classes won't get pulled into your application and bloat its binary size).

For example the Gtk.Window class, class type and constructors are available in the Ocgtk_Gtk.Gtk.Window module, which looks like this:

(* The class type, returned by a constructor function *)
class type  window_t 

(* The class itself, never used directly (only if you are bridging L1 -> L2) *)
class window : [ `window | `widget | `initially_unowned | `object_ ] Gobject.obj -> window_t

(* Constructor, used to create a new instance *)
val new_ : unit -> window_t

Class types are named in full so that they can be disambiguated in hover and type-preview via LSP/merlin.

Creating objects

Use a constructor in a class's module to instantiate it, for example:


open Ocgtk_gtk.Gtk

let () =
  let _ = Ocgtk.GMain.init () in
  let window = Window.new_ () in
  ...

Interfaces are also classes in OCaml, but they won't have constructor functions. This is also the same for abstract classes. For both of these, you will get values indirectly as the result of calling methods on other objects.

Inheritance and interfaces

How inheritance and interface implementation is implemented in OCaml

Classes and Interfaces are represented as a class type and a class in OCaml. The OCaml class type for each GObject class/interface will inherit both its base class and each of its interfaces.

(Unlike GOBject's single-inheritance + interfaces, OCaml supports multiple inheritance).

For example in GObject, the Window class inherits from Widget and implements Accessible, Buildable, ConstraintTarget, Native, Root and ShortcutManager.

In OCaml, this will look something like:

class type window_t = object
  (* base class *)
  inherits Widget.widget_t

  (* implements *)
  (* The other interfaces would appear here, but widget_t already inherits them, so they are skipped *)
  inherits Native.native_t
  inherits Root.root
  inherits ShortcutManager.shortcut_manager_t

end

Note that Widget already implements Accessible, Buildable and ConstraintTarget, so they won't be added again to the definition of Window.

Upcasting: how to pass subclass values and use polymorphism

Say you have a button_t, but you want to pass it as a value to a method that declares a parameter of widget_t. Unlike other object-oriented languages where you can pass this directly, OCaml requires you to explicitly upcast it using the :> operator.

For example, Box#append takes a widget_t, so a button must be upcast before it can be added to a box:

open Ocgtk_gtk.Gtk

let build_layout () =
  let box = Box.new_ `VERTICAL 10
  let button = Button.new_with_label "Click me"

  (* Type error: button has type button_t, but append expects widget_t *)
  let () = box#append button

  (* Correct: upcast with :> *)
  let () = box#append (button :> Widget.widget_t)

The same applies wherever a method takes a widget_t. For example, window#set_child (Some (box :> Widget.widget_t)) passes a box_t to a parameter of type widget_t option.

Cyclic groups and top-level classes

You may notice references to modules like Application_and__window_and__window_group in the documentation and the source code. This is because some GObject classes and/or interfaces have mutually recursive dependencies between them.

In OCaml, these can't be declared in separate files, but instead need to be declared in a OCaml recursive cluster in the same file i.e. class type c1 ... and c2 .. end / class c1 ... and c2 ... end. Each individual class is then aliased in a separate module to "flatten" the namespace and hide the recurive classes.
